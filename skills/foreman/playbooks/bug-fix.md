### Bug fix

**You own this task. Plan, review, verify.** Delegate investigation and the fix to subagents, stay in the lead. Pick each subagent's reasoning level for the job, per the Subagents section.

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

1. Check it isn't already done. `git fetch`, then look for the issue number or symptom keywords in the integration branch's recent log (`git log origin/<integration> --since=3.days --grep <issue# or keywords>`) and in open and merged PRs (`gh pr list --state all --search "<issue# or keywords>"`). If a merged change already covers it, verify that fix on the integration branch with the cheapest proof, report, set the run `done`, and stop without a new branch. If an open PR or branch is already on it, stop and tell the owner instead of building in parallel.
2. Reproduce it yourself, within `## Reproduce` in the project file, on the matching surface with a real driver (Non-negotiables), even when a debug or instrumentation protocol says to ask the user to reproduce. Ask the user only with a stated, specific reason the control surface cannot reach the target, and only after driving it as far as it goes. If it won't reproduce directly, synthesize the trigger, tighten conditions, or instrument until it fires.
3. Binary-search the cause. Form the candidate hypotheses, then rule them out until one survives. Seed them with `how` over the affected subsystem and the **why** skill for regression history. Each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. When program state is unclear, add instrumentation or logging and read it as the code runs. Don't guess. Drive a long or stubborn hunt with Claude Code's `/loop` command. Confirm the surviving *mechanism* with runtime evidence before the step-4 architect/interrogate fan-out. If the proven cause already has a fix, merged or in an open PR, that is a normal ending. Report the cause, link the existing fix, set the run `done`, and land nothing.
4. Plan the fix. If it crosses a function boundary, `architect` first. Delegate implementation to a subagent using `model: "sonnet"`, `effort: "high"` (the code-delegate default) with a specific scope.
5. Verify on the same surface. The original repro now passes. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence. Prove it per `## Proof` in the project file. Proof must be able to fail: a test or screenshot that also passes on the base branch proves nothing.
6. Size the change per `## Sizing` in the project file. A big change gets a code review and a break-it check in a fresh subagent before you land, per the project's Step map. Without a project file, use the plugin defaults.
7. Stage the commits so the failing repro lands before the fix in git history. See the **tdd** skill for the failing-test-first cadence when the bug has a cheap local test path. Skip it when the test would be expensive, integration-heavy, or unclear.
   This is the canonical **Sequence Work into Verifiable Units** principle, the failing test first and the fix on top.
8. If the fix needs a schema change, write the migration file and code on the branch, then pause. After the yes, apply it per the project's rules, verify, re-prove, then continue. Never land code that depends on an unapplied migration.
9. Land via the Step map `land` entry. Without a project file, run **Opening a PR**.

**Reply:** what was broken, root cause, fix, how you verified. Paste failing-then-passing repro output verbatim.
